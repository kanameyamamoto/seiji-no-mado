# 運用のしかた

## 1. 何が、どう更新されるか

サイトの中身は、更新のしかたで3つに分かれます。

| 種類 | 対象 | どう更新するか | いつ |
|---|---|---|---|
| **機械** | 会派別の所属議員数（衆議院・参議院） | 両院の「会派別所属議員数」のページから、そのまま数字を取る（`mechanical.py`） | 毎日 |
| | 国会の会期（召集日・終了日）、新しい国会 | 衆議院「国会会期一覧」から取る。新しい国会は自動で追加し、閉会から60日たつと毎日の確認から外す | 毎日 |
| | 法律の公布日・法律番号 | 成立のあとに決まるので、参議院の議案情報から後追いで入れる | 毎日 |
| | 国会議員の一覧（衆・参）と、参議院議員一人ひとりの賛否 | 両院の公式の議員一覧と、参議院の本会議投票結果から取る（`people.py`） | 毎日 |
| | 知事の一覧 | 全国知事会「現職知事一覧」（PDF）から取る | 毎日 |
| | 審議中・採決されなかった法律案の一覧（審議中・継続審査・審議未了・撤回。否決されたものは記事の下書きを作るためだけに使う） | 衆議院「議案の一覧」と法案ごとの「議案審議経過情報」から、題名・提出者・提出会派・結果をそのまま取る（`bills.py`）。経過情報は審議状況が変わったときだけ読み直す | 毎日 |
| **AI（新しく書く）** | 国会で決まったこと（法律・予算・条約と、否決された法律案） | 成立したものは参議院の議案情報から、否決されたものは `bills.json` から見つけ（衆議院で否決→衆議院の経過情報の賛成・反対会派と議案要綱、参議院で否決→参議院の議案要旨と投票結果）、番号・日付・賛否は機械で、文章は Claude（スケジュール）が書く。機械と Gemini で確かめる（`update_laws.py` → `ai_draft.py`） | 毎日 |
| **AI（説明を足す）** | 法律の記事の「なぜ出されたか・だれに関係するか・国会での議論」 | 法律案の「理由」（衆議院の議案本文）と、国会会議録（国立国会図書館のAPI）の委員長報告・討論を機械で集め、Claude が書き、機械と Gemini で確かめる（`deliberation.py` → `enrich.py`）。会議録の公開を待ってから足す | 毎日、上限は `config.json` の `more` |
| **AI（見直す）** | 学ぶ（110ページ）・つながり（37ページ）・政党（22党）・選挙の結果・メディア | 出典と照らして、食い違うところだけを直す（`recheck.py`）。きっかけは下の3つ | 毎日、上限3ページ |
| **検索用のページ・公開API** | 全ページ（約990）と、同じ中身の JSON（`api/v1/`）、AI 向けの案内（`llms.txt`） | 公開のたびに、データから書き出し直す（`prerender.py`）。サイトマップも作る | 公開のたび |

### 見直しのきっかけ

1. **出典が変わった**：週に1回、すべての出典（約700）を見に行く（`watch_sources.py`）。
   法令は e-Gov の改正履歴、PDFは本文、そのほかのページは本文を比べる。日付や「更新日」の表示だけの変化は無視する。
2. **出典の法律を改正する法律が成立した**：その法律を出典にしているページを、すぐ見直し待ちにする（`publish.py`）。
3. **確認日から日数がたった**：出典に変化がなくても、政党60日・選挙とつながり180日・学ぶとメディア365日で見直す（ルールC-5）。
   日数と1日の上限は `data/config.json` の `recheck` で変えられる。

**パブリックコメントと閣議の案件（ルール D-14・D-15）**：毎日の機械の更新（`mechanical.py`）で、e-Gov パブリック・コメントの RSS（意見募集・結果公示）と、首相官邸の「閣議」のページを読む（`steps.py` → `data/pubcom.json`・`data/kakugi.json`）。RSS には最近のものしか出ないので、パブコメは毎日足していく。閣議は `config.json` の `steps.kakugi_from_year` の年から。読んだ閣議のページは読み直さない。「人事」の区分は載せない。審議会は、まとまった公式の一覧がないため、まだ入れていない。

**国の予算事業と支出先（ルール D-13）**：週1回の見張り（`watch.yml`）で、行政事業レビュー見える化サイト（RSシステム）の CSV を読み直す（`rs.py` → `data/rs/`）。中身が変わっていなければ何も書かない。新しい年度のレビューシートが公開されたら、`data/config.json` の `rs.year` を変える。支出先の名前は正しい法人番号のあるものだけ（9999999999999 などの仮の番号は外す）。検索の箱（D1）にはまだ入れていない（無料枠の1日の書き込み上限をこえるため。Workers の有料プランにしたら入れる）。

**質問主意書と答弁書（ルール D-12）**：毎日の機械の更新（`mechanical.py`）で、衆議院・参議院の質問主意書の一覧を読み、答弁がまだのものだけ明細を読み直す（`questions.py` → `data/questions.json`）。対象の国会は `data/config.json` の `questions.from_session`、1回に読む明細の上限は `questions.detail_limit`。提出者は今の議員の一覧と名前で照らし合わせ、議員ページにも出す。

**公式サイト・SNS（ルール D-11）**：同じ週1回の見張り（`watch.yml`）で、政府・国会・政党の公式サイトと、そこにリンクされているSNSアカウントを集め直す（`accounts.py` → `data/accounts.json`）。集める組織と、トップページにSNSのリンクがないときに使う「SNSの一覧ページ」は `data/accounts_src.json` に書く（政党は `data/parties.json` の `url`）。公式サイトを読めなかった組織は、前回の結果のまま `unreachable` に日付が入る。

会派の人数が変わった政党（統一会派の党）も、見直し待ちになります。

### 見直しで直すとき

- AIは「どこを（場所）・前の文・後の文・根拠の出典」を出す。ページの形（項目の数や並び）は変えない。
- 前の文が今のページと一字一句同じか、後の文の新しい数字・日付が出典にあるかを、機械で確かめる（C-2）。
- 別の会社のAI（Gemini）が、根拠・必要性・評価語・偏り・読むレベルのそろい方を確かめる（C-1）。
- 通ったら直して公開し、ページの「作成と更新の記録」に、いつ・何を直したかとチェックの記録へのリンクを載せる（C-4・T-2）。
- 食い違いがなければ、確認日だけを今日にする（P-4）。

### 人が見る必要があるもの

自動では公開しないものは、**直した版をAIが作ってプルリクエストで提案**します。山本さんは中身を見て「Merge」を押すだけです（押すと公開されます）。
直した版を作れなかったときだけ、Issue（ラベル「要確認」）で知らせます。

| こと | 自動でやること | 人がやること |
|---|---|---|
| 形を変える直し（項目の追加・削除など） | AIが直した版を作り、機械と別の会社のAIで確かめて、プルリクエストにする | 見て Merge |
| 会派の組み替え（会派ができた・なくなった・統一会派の人数が変わった） | 関係する党のページを見直し待ちにし、会派名・人数・説明を直した版をプルリクエストにする | 見て Merge |
| リンク切れ（出典が3週続けて開けない） | AIがウェブ検索で代わりの出典を探し、開けること・元の文の根拠になることを確かめて、プルリクエストにする | 見て Merge |
| 法律の記事が公開されなかった | （議案要旨が出たら自動でやり直す） | 3回書き直しても通らないときだけ、Issue を見て直す |
| どの党の会派か自動で決められない | Issue で知らせる | Issue を見て直す |
| **選挙のあと** | 選挙のページの出典が変わったときは見直す | **新しい選挙の結果を足すのは人の作業**（各党の獲得議席の列を足すなど、データの形が変わるため）。次は2028年夏の参院選の予定（衆議院が解散されればその前） |

**最初に1回だけ必要な設定**：GitHub Actions がプルリクエストを作れるようにします（作れない間は、同じ中身が Issue で届きます）。

```sh
gh api -X PUT repos/kanameyamamoto/seiji-no-mado/actions/permissions/workflow -f default_workflow_permissions=read -F can_approve_pull_request_reviews=true
```

（画面からなら Settings → Actions → General → 一番下の「Allow GitHub Actions to create and approve pull requests」をオン）

## 2. 手で更新するとき

GitHub の「Actions」から、次のワークフローを「Run workflow」で動かせます。

- 「毎日の更新」：回次を入れると、その国会だけを確かめます（空なら `config.json` のとおり）
- 「出典の見張り」：すぐに出典を確かめたいとき

1つのページだけ見直したいときは、手元で `python pipeline/recheck.py --unit learn:what-is-politics`。

## 3. 最初の設定（1回だけ）

### 書く担当と確かめる担当

- **書く担当：Claude のスケジュール**（毎朝 7:23 ごろ）。Claude のプランの中で動くので、追加の料金はかからない。
  GitHub が `work/requests/` に置いた依頼に答え、`work/answers/` に置いて push する。手順は [claude-writer.md](claude-writer.md)。
  push すると「毎日の更新」がすぐに動いて、確かめてから公開する。書き直しが必要なら、その場で最大3回くり返す。
- **確かめる担当：Google Gemini（無料枠）**。キーを1つ登録する：
  1. https://aistudio.google.com/apikey で「APIキーを作成」
  2. `gh secret set GEMINI_API_KEY -R kanameyamamoto/seiji-no-mado`（実行するとキーを聞かれるので貼る）

キーがない間は、AIの部分はなにもしません（法律は下書きのまま、見直しは見直し待ちのまま残ります）。機械の更新と出典の見張りは、キーがなくても動きます。
Gemini の無料枠の回数の上限に当たった日は、失敗にはせず、次の回に回します。

### 費用

- GitHub（自動処理・公開）：0円（公開リポジトリは無料）
- 書く担当（Claude のスケジュール）：0円（今の Claude のプランの利用枠を使う。ふだんのチャットと同じ枠）
- 確かめる担当（Gemini 無料枠）：0円

量の目安：法律の記事は国会が開いている間に月20件ほど、ページの見直しは1日3ページまで（`data/config.json` の `recheck`）。

API で動かすこともできます（`WRITER=api`・`CHECKER=openai` と各社のキー。そのときは使った分の料金がかかる）。

### Google に登録する（検索に出るように）

1. https://search.google.com/search-console を開き、「プロパティを追加」→「URL プレフィックス」に `https://seijinomado.com/` を入れる（2026年11月2日に、住所を `kanameyamamoto.github.io/seiji-no-mado/` から `seijinomado.com` に変えた。古い住所は GitHub が新しい住所へ転送する）
2. 所有権の確認で「HTML タグ」を選び、出てきた `<meta name="google-site-verification" content="...">` の content の値を Claude に渡す（index.html に入れて公開する）
3. 確認できたら、左の「サイトマップ」に `sitemap.xml` を入れて送信する

検索用のページ（`/a/…/`・`/learn/…/` など）とサイトマップは、公開のたびに自動で作り直されます。

2026年11月1日に登録済み。`index.html` の `google-site-verification` のタグ（2つ。古い住所用と seijinomado.com 用）は、消すと登録が外れるので消さないこと。

### 検索API・MCP（api.seijinomado.com。ルール S-1〜S-3）

公開しているデータを読むだけの小さなサーバー（Cloudflare Workers）と、データの箱（Cloudflare D1）。
データが変わるたびに `.github/workflows/api.yml` が、`pipeline/db.py` で箱の中身（SQL）を作り、中身が変わっていたら入れ替えて、`worker/` を公開する。

- 入口：`GET /v1/search?q=…`・`GET /v1/{種類}`・`GET /v1/{種類}/{id}`・`POST /mcp`（AI からの入口）。使い方は https://api.seijinomado.com/
- 記録をとらない（S-2）：Worker はログを出さず、`wrangler.toml` でログ・トレースも切っている。回数の上限（1分60回）のための数え方だけは Cloudflare の中で1分だけ使う。
- 費用：Cloudflare の無料枠（Workers 1日10万回・D1 読み出し1日500万行・書き込み1日10万行）の中。超えると、その日は止まる（勝手にお金はかからない）。

最初の設定（1回だけ。Cloudflare のキーは、チャットに貼らずに直接 GitHub に入れる）：

1. Cloudflare の画面右上の人のアイコン →「プロフィール」→「API トークン」→「トークンを作成」→「カスタムトークンを作成」
2. 権限を4つ足す
   - アカウント ／ D1 ／ 編集
   - アカウント ／ Workers スクリプト ／ 編集
   - ゾーン ／ Workers ルート ／ 編集
   - ゾーン ／ DNS ／ 編集
   「ゾーン リソース」は「特定のゾーン」→ `seijinomado.com`
3. 作ったトークンを GitHub に入れる：`gh secret set CLOUDFLARE_API_TOKEN -R kanameyamamoto/seiji-no-mado`（聞かれたら貼る）
4. アカウント ID（Cloudflare のホームで、アカウント名の横の「…」→「アカウント ID をコピー」）を入れる：`gh secret set CLOUDFLARE_ACCOUNT_ID -R kanameyamamoto/seiji-no-mado`
5. GitHub の Actions →「検索APIとMCPの公開」→「Run workflow」。D1 の作成・中身の入れ替え・Worker の公開・`api.seijinomado.com` の住所づけまで自動で行う。

設定が入るまでは、このワークフローは何もせずに終わります（サイトには影響なし）。

動きはじめたら：

- `data/config.json` に `"api_live": true` を足す（llms.txt に MCP と検索API の案内が出る。サイトの「データを使う」のページは、入口が動いているかを自分で確かめて「使えます」と出す）。
- `.github/workflows/mcp-registry.yml` が、MCP の公式一覧（registry.modelcontextprotocol.io）に `server.json` の中身で自動で載せる（GitHub の OIDC でログインするので鍵はいらない）。中身を変えて載せ直すときは `server.json` の `version` を上げる。

### SNS への投稿（Bluesky・X。ルール D-17）

`.github/workflows/social.yml` が、「毎日の更新」「公開」のあとと、毎日12:17に `pipeline/social.py` を動かす。
成立などの日から30日以内の記事で、まだ出していないものを、決まった形（種類・題名・日付・要約〈ふつう〉・リンク）で、古い順に1回10件まで投稿する。
記事のページがまだ見られないときは、次の回に回す。出した記録は `work/social.json`。
`python pipeline/social.py --dry-run` で、出す文だけを確かめられる（投稿はしない）。

鍵がないSNSには何もしない。鍵は、チャットに貼らずに直接 GitHub に入れる：

- Bluesky（無料）：アカウントを作る →「設定」→「プライバシーとセキュリティ」→「アプリパスワード」で作る
  - `gh secret set BLUESKY_HANDLE -R kanameyamamoto/seiji-no-mado`（例：seijinomado.bsky.social。あとで seijinomado.com にもできる）
  - `gh secret set BLUESKY_APP_PASSWORD -R kanameyamamoto/seiji-no-mado`
- X（投稿ごとにお金がかかる）：アカウントを作る → developer.x.com でアプリを作り、権限を「Read and write」にしてから、4つのキーを作る
  - `X_API_KEY`・`X_API_SECRET`（Consumer Keys）、`X_ACCESS_TOKEN`・`X_ACCESS_SECRET`（Access Token and Secret）を、上と同じく `gh secret set` で入れる
  - 権限を変えたあとに Access Token を作り直さないと、投稿で 403 になる

### 住所（ドメイン）

- `seijinomado.com`（Cloudflare Registrar で登録。自動更新オン）。サイトは今までどおり GitHub Pages に置き、Cloudflare の DNS で GitHub Pages を指す（プロキシはオフ＝DNS only）。
- GitHub の Settings → Pages の「Custom domain」に `seijinomado.com` を入れている。住所を変えるときは、ここと `data/config.json` の `site_url` を両方変える。

## 4. 人が見る必要があるものの直し方

- **法律の記事**：`data/pending/<名前>.json` の `status` を `fetched` に戻すと、次の更新でもう一度試します。
  人が書くときは `data/feed.json` に直接足し、下書きのファイルを消します。
- **提案のプルリクエスト**：「Files changed」で変わるところを見て、よければ「Merge pull request」。よくなければ「Close」（そのページは14日後にまた自動で見直されます）。
- **ページ**：`data/logs/recheck/` の記録に、どこが問題だったかが残っています。人が直したら、そのページの `updates` に記録を足し、`checked` を今日にします。
  `data/watch.json` の `held` からそのページを消すと、自動の見直しにも戻ります（消さなくても14日後に戻ります）。

片づいたら Issue を閉じます。

## 5. 間違いを直すとき（ルールT-2）

1. Issue「訂正の依頼」で受け付ける
2. 出典と照らし合わせて確かめる
3. `data/` のファイルを直し、プルリクエストを作る（チェックが自動で動きます）
4. 何をいつどう直したかを、そのページ・記事の `corrections` に残す
   例：`"corrections": [{"date": "2026-11-05", "text": "施行日を「令和9年4月1日」に訂正（元は4月10日）。"}]`
5. 取り込むと、自動で公開されます。ページの「作成と更新の記録」に表示されます

## 6. ルールを変えるとき（ルールT-1）

1. Issue「ルール変更の提案」で、変更案と理由を公開する
2. しばらく意見を待ってから、`data/rules.json` を直すプルリクエストを作る
3. `version` を上げ、`history` に「いつ・何を・なぜ」を足す
4. AIの書き方に関わるときは、`prompts/` の指示文も同じプルリクエストで直す

## 7. 手元で試すとき

```sh
pip install -r requirements.txt
python pipeline/validate.py                 # 公開前のチェック
python pipeline/mechanical.py               # 機械の更新
python pipeline/watch_sources.py --limit 20 # 出典の見張り（20件だけ）
python pipeline/recheck.py --list           # 今日見直すページを表示するだけ
python -m http.server 8000                  # http://localhost:8000 でサイトを見る
```
