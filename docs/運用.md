# 運用のしかた

## 1. 何が、どう更新されるか

サイトの中身は、更新のしかたで3つに分かれます。

| 種類 | 対象 | どう更新するか | いつ |
|---|---|---|---|
| **機械** | 会派別の所属議員数（衆議院・参議院） | 両院の「会派別所属議員数」のページから、そのまま数字を取る（`mechanical.py`） | 毎日 |
| | 国会の会期（召集日・終了日）、新しい国会 | 衆議院「国会会期一覧」から取る。新しい国会は、載せる範囲の年なら自動で追加 | 毎日 |
| | 法律の公布日・法律番号 | 成立のあとに決まるので、参議院の議案情報から後追いで入れる | 毎日 |
| **AI（新しく書く）** | 国会で決まったこと（法律・予算・条約） | 参議院の議案情報から見つけ、番号・日付・賛否は機械で、文章はAIが書く。機械と別の会社のAIで確かめる（`update_laws.py` → `ai_draft.py`） | 毎日 |
| **AI（見直す）** | 学ぶ（110ページ）・つながり（37ページ）・政党（22党）・選挙の結果・メディア | 出典と照らして、食い違うところだけを直す（`recheck.py`）。きっかけは下の3つ | 毎日、上限8ページ |

### 見直しのきっかけ

1. **出典が変わった**：週に1回、すべての出典（約700）を見に行く（`watch_sources.py`）。
   法令は e-Gov の改正履歴、PDFは本文、そのほかのページは本文を比べる。日付や「更新日」の表示だけの変化は無視する。
2. **出典の法律を改正する法律が成立した**：その法律を出典にしているページを、すぐ見直し待ちにする（`publish.py`）。
3. **確認日から日数がたった**：出典に変化がなくても、政党30日・選挙とつながり90日・学ぶ180日・メディア365日で見直す（ルールC-5）。
   日数と1日の上限は `data/config.json` の `recheck` で変えられる。

会派の人数が変わった政党（統一会派の党）も、見直し待ちになります。

### 見直しで直すとき

- AIは「どこを（場所）・前の文・後の文・根拠の出典」を出す。ページの形（項目の数や並び）は変えない。
- 前の文が今のページと一字一句同じか、後の文の新しい数字・日付が出典にあるかを、機械で確かめる（C-2）。
- 別の会社のAIが、根拠・必要性・評価語・偏り・読むレベルのそろい方を確かめる（C-1）。
- 通ったら直して公開し、ページの「作成と更新の記録」に、いつ・何を直したかとチェックの記録へのリンクを載せる（C-4・T-2）。
- 食い違いがなければ、確認日だけを今日にする（P-4）。

### 人が見る必要があるもの

自動では決めないものは、Issue（ラベル「要確認」）で知らせます。

| 知らせ | 起きること |
|---|---|
| 法律の記事が公開されなかった | 議案要旨がまだない、または3回書き直してもチェックに通らなかった |
| ページを直せなかった | 項目を足す・消すなど形を変える直しが必要、3回出し直しても通らない、出典が開けない |
| 会派が変わった | 新しい会派ができた・なくなった。各党の `members.kaiha_shu` / `kaiha_san` を直す |
| 範囲の外の国会 | 載せる範囲（feed.json の criteria、今は2026年）の外の年に国会が召集された |
| リンク切れ | メディアの一覧のリンクが3回続けて開けない |

**選挙のあと**は、人の作業が必要です（選挙結果の追加、各党の獲得議席の列の追加など、形が変わるため）。
選挙のページの出典が変わると見直し待ちになり、AIが「形を変える直しが必要」と判断して Issue で知らせます。

## 2. 手で更新するとき

GitHub の「Actions」から、次のワークフローを「Run workflow」で動かせます。

- 「毎日の更新」：回次を入れると、その国会だけを確かめます（空なら `config.json` のとおり）
- 「出典の見張り」：すぐに出典を確かめたいとき

1つのページだけ見直したいときは、手元で `python pipeline/recheck.py --unit learn:what-is-politics`。

## 3. 最初の設定（1回だけ）

### APIキー

「Settings」→「Secrets and variables」→「Actions」→「Secrets」に2つ登録します。

| 名前 | 中身 |
|---|---|
| `ANTHROPIC_API_KEY` | 書く担当・見直し担当（Anthropic）のAPIキー |
| `OPENAI_API_KEY` | 確かめる担当（OpenAI）のAPIキー |

キーがない間は、AIの部分はなにもしません（法律は下書きのまま、見直しは見直し待ちのまま残ります）。機械の更新と出典の見張りは、キーがなくても動きます。

### モデル名（任意）

同じ画面の「Variables」に `WRITER_MODEL`・`CHECKER_MODEL` を登録すると、使うモデルを変えられます。
登録しないときは、ワークフローに書いた既定のモデルを使います。使ったモデル名は、チェックの記録（`data/logs/`）に残ります。

### 費用の目安

- 法律の記事：1件あたり、書く・確かめる・書き直しを合わせて数万トークン程度。2026年の第221回国会（約5か月）で98件。
- 見直し：1ページあたり、出典の抜粋（最大8つ×12,000字）を読むので、数万〜10万トークン程度。1日の上限は8ページ（`data/config.json`）。

各社の料金表で、使うモデルの単価をかけて確かめてください。費用をおさえたいときは `recheck.daily_limit` を小さくします。

### GitHub Pages

「Settings」→「Pages」→「Build and deployment」の Source を「GitHub Actions」にします（設定済み）。

## 4. 人が見る必要があるものの直し方

- **法律の記事**：`data/pending/<名前>.json` の `status` を `fetched` に戻すと、次の更新でもう一度試します。
  人が書くときは `data/feed.json` に直接足し、下書きのファイルを消します。
- **ページ**：`data/logs/recheck/` の記録に、どこが問題だったかが残っています。人が直したら、そのページの `updates` に記録を足し、`checked` を今日にします。
  `data/watch.json` の `held` からそのページを消すと、自動の見直しにも戻ります（消さなくても14日後に戻ります）。

片づいたら Issue を閉じます。

## 5. 間違いを直すとき（ルールT-2）

1. Issue「訂正の依頼」で受け付ける
2. 出典と照らし合わせて確かめる
3. `data/` のファイルを直し、プルリクエストを作る（チェックが自動で動きます）
4. 何をいつどう直したかを、そのページ・記事の `corrections` に残す
   例：`"corrections": [{"date": "2026-11-05", "text": "施行日を「令和9年4月1日」に訂正（元は4月10日）。"}]`
5. 取り込むと、自動で公開されます。ページの「作成と更新の記録」に表示されます

## 6. ルールを変えるとき（ルールT-1）

1. Issue「ルール変更の提案」で、変更案と理由を公開する
2. しばらく意見を待ってから、`data/rules.json` を直すプルリクエストを作る
3. `version` を上げ、`history` に「いつ・何を・なぜ」を足す
4. AIの書き方に関わるときは、`prompts/` の指示文も同じプルリクエストで直す

## 7. 手元で試すとき

```sh
pip install -r requirements.txt
python pipeline/validate.py                 # 公開前のチェック
python pipeline/mechanical.py               # 機械の更新
python pipeline/watch_sources.py --limit 20 # 出典の見張り（20件だけ）
python pipeline/recheck.py --list           # 今日見直すページを表示するだけ
python -m http.server 8000                  # http://localhost:8000 でサイトを見る
```
